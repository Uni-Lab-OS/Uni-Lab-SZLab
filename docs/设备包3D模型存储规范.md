# Uni-Lab 领域设备包 3D 模型存储规范

## 1. 目标与适用范围

本规范定义设备或资源的 3D/2.5D 模型如何随领域设备包一起安装、发现、校验和读取。目标是：

- 引用一个设备包时，同时获得驱动、动作、资源、工作流和模型；
- workspace、editable install、wheel 和远端缓存包使用同一套相对路径语义；
- 模型身份只绑定在 `@device` 或 `@resource`，不再维护包级第二份发现协议；
- 设备专属资产与驱动共同演进，移动设备目录时能整体迁移；
- 未选中的设备可以被静态发现，但不会因此实例化、连接硬件或执行 Xacro。

本文中的“必须”“禁止”“推荐”分别表示规范性要求、不可接受做法和默认选择。

## 2. 仓库与 Python 包边界

领域仓库根必须同时是 Python distribution root 和 OS workspace root：

```text
Uni-Lab-SZLab/
├── pyproject.toml
├── szlab_poly_studio/              # 唯一顶层 import package
│   ├── devices/
│   ├── resources/
│   ├── workflows/
│   ├── profiles/
│   └── common/
├── deployment/
├── tests/
├── docs/
├── scripts/
└── migration/
```

禁止增加 `packages/` 中间层。一个 import package 可以包含任意多个设备、资源和工作流；
“一个 distribution”不等于“一个设备”。

## 3. 资产放置位置

### 3.1 设备专属模型

```text
<import_package>/devices/<device_id>/
├── device.py
├── models/
│   ├── device.xacro
│   ├── meshes/
│   │   ├── base.stl
│   │   └── arm.dae
│   ├── textures/
│   ├── config/
│   └── shape.yml
└── ...
```

`<device_id>` 必须与 `@device(id="...")` 的稳定机器 ID 一致。设备模型禁止放到仓库根的共享
`models/`，也不应塞进 `scripts/`、`deployment/` 或运行时数据目录。

### 3.2 资源专属模型

```text
<import_package>/resources/<resource_id>/models/
├── resource.xacro
├── meshes/
├── textures/
└── shape.yml
```

资源 ID 必须与 `@resource(id="...")` 一致。两个资源确实使用同一几何时，可以在构建阶段从
一个明确的源生成两份闭包，或者等待 Catalog schema 提供受控的包内共享引用；禁止使用逃出
Python 包根的 `../../..` 路径。

## 4. 装饰器是唯一模型绑定点

### 4.1 Xacro 默认写法

```python
@device(
    id="szlab_mixer_robot",
    display_name="SZLab 搬运机械臂",
    category=["robotic_arm", "material_transport"],
    model={
        "format": "xacro",
        "entry": "models/device.xacro",
        "macro": "szlab_mixer_robot",
    },
)
class SzlabMixerRobotDevice:
    ...
```

`entry` 相对声明该装饰器的 `device.py` 解析，而不是相对进程当前目录、仓库根或 OS 安装目录。

当 `format == "xacro"` 时，这一个入口默认同时表达：

- Web 可视化的几何与关节树；
- kinematics 使用的 link/joint 结构；
- collision 使用的碰撞几何。

因此禁止为了形式完整，把同一个 Xacro 重复写成三份 `web/kinematics/collision` 配置。只有
确实生成了不同资产时才增加覆盖，例如 Web 使用轻量 GLB、碰撞使用凸包 URDF：

```python
model={
    "format": "xacro",
    "entry": "models/device.xacro",
    "macro": "szlab_mixer_robot",
    "overrides": {
        "web": {"format": "glb", "entry": "models/web/device.glb"},
        "collision": {"format": "urdf", "entry": "models/collision/device.urdf"},
    },
}
```

### 4.2 2.5D 外形

没有真实 3D 模型时，可以绑定轻量外形作为前端回退：

```python
model={
    "shape": {
        "format": "unilab.shape/v1",
        "entry": "models/shape.yml",
    },
}
```

之后加入 Xacro 时，在同一个 `model` 字典增加 `format/entry/macro`，保留 `shape` 作为低带宽
或加载失败时的回退。不要恢复全包外形清单。

本规范把轻量外形文件统一命名为 `shape.yml`。这是当前 OS 兼容期的明确约束：旧
`--devices` 加载器会把 `devices/` 或 `resources/` 子树中的 `*.yaml` 误认为旧式注册表，可能
改写模型文件；`.yml` 仍是标准 YAML，且模型由装饰器中的显式 `entry` 定位，不依赖扩展名
发现。Issue #147 的 PackageCatalog 取代旧加载器后，可以同时接受 `.yml` 和 `.yaml`，但包内
应保持一种命名，避免无意义的格式分叉。

## 5. Xacro 与 `mesh_path`

推荐继续使用 Xacro，尤其是有关节、宏参数、多个 mesh、碰撞体或 MoveIt 配置的设备。静态、
无关节且只服务浏览器的资源可以直接用 GLB；简单刚体也可用 URDF。

Xacro 中可以保留 `mesh_path` 参数：

```xml
<xacro:macro name="szlab_mixer_robot" params="mesh_path prefix:=''">
  <mesh filename="${mesh_path}/meshes/base.stl"/>
</xacro:macro>
```

但 `mesh_path` 的值必须由 Edge 的资产 Source Adapter 注入：

- workspace：注入 `device.py` 同级的 `models/` 绝对路径；
- installed distribution：通过 `importlib.resources` 定位 wheel 中的 `models/`；
- cached archive：注入校验、解包后的只读缓存资产根；
- Web：Edge 返回受控资产 URL 根，不向浏览器泄露服务器绝对路径。

用户不需要手改 Xacro 的本机绝对路径，也不需要在打包前批量替换路径。构建脚本只负责校验
闭包和生成 Catalog，不应重写源文件。

## 6. 模型目录应包含什么

按需包含：

- 主入口：`device.xacro`、`resource.xacro`、`.urdf` 或 `.glb`；
- 几何：STL、DAE、OBJ/MTL、GLTF/GLB；
- 贴图：PNG/JPEG 等；
- 运动学/控制配置：仅在设备确实需要时放入 `config/`；
- 2.5D 回退：`shape.yml`；
- 资产许可证和来源说明：第三方 CAD/mesh 必须可追溯。

生产示教点、现场标定结果、密钥、IP、操作者和运行日志禁止进入通用 wheel。机器人点位合同可
随包，现场 pose 与 calibration revision 应由部署侧权威存储维护。

## 7. 打包要求

`pyproject.toml` 必须包含所有资产类型：

```toml
[tool.setuptools.package-data]
szlab_poly_studio = [
  "**/*.yaml", "**/*.yml", "**/*.xacro", "**/*.urdf",
  "**/*.stl", "**/*.dae", "**/*.obj", "**/*.mtl",
  "**/*.gltf", "**/*.glb", "**/*.png", "**/*.jpg", "**/*.jpeg",
]
```

构建检查必须在干净 wheel 中验证：

1. 每个装饰器 `model.entry` 是静态字符串；
2. 路径相对声明文件解析并位于 import package 内；
3. 入口和它引用的 include、mesh、texture 均存在；
4. symlink 不逃出资产根；
5. wheel 安装后仍能得到同一个资产闭包；
6. workspace Catalog 与 clean-wheel Catalog 一致。

## 8. Edge 读取流程

目标 OS 的读取链路是：

```text
workspace / installed wheel / cached archive
                │
                ▼
        PackageCatalogCompiler
        ├── AST 读取装饰器元数据
        ├── 解析声明文件位置
        ├── 校验 model.entry 与资产闭包
        └── 生成统一 PackageCatalog
                │
        ┌───────┴────────┐
        ▼                ▼
  Registry/Runtime   Edge asset API
                          │
                          ▼
                     Web / Xacro consumer
```

发现阶段只读 AST 和静态资产，不 import 驱动、不执行 Xacro、不实例化设备。Graph/Profile 选中
某个设备后，运行时才允许 import 驱动；Web 请求模型时，Edge 再通过 Catalog 中的声明位置读取
已校验资产。

当前 OS 的 `--workspace` 和统一 Catalog 尚需 Issue #147 的 OS delivery 实现；在此之前，包的
目录和装饰器已经按目标合同准备好，但旧 `--devices` 入口只承担兼容扫描，不能被视为完整的
模型资产协议。

## 9. 安全与版本规则

- 拒绝绝对路径、路径逃逸和资产根外 symlink；
- 不根据设备名称猜文件路径；
- 不允许浏览器直接读取服务器文件系统；
- 模型变化随 distribution 版本发布，Catalog 记录版本和 digest；
- 超大 CAD 源文件是否进包由许可证和体积策略决定，运行必需的派生资产必须进入 wheel；
- 模型解析失败应产生明确诊断，不得静默连接硬件或使用错误设备模型。

## 10. 提交检查清单

- [ ] 模型位于对应设备/资源的 `models/`；
- [ ] `@device/@resource` 直接绑定模型；
- [ ] Xacro 只声明一次默认入口；
- [ ] `mesh_path` 由 Edge 注入，无本机绝对路径；
- [ ] package-data 覆盖完整资产类型；
- [ ] workspace 与 wheel 中的相对路径一致；
- [ ] 未携带现场点位、密钥或运行数据；
- [ ] 许可证和来源可追溯；
- [ ] 不存在包级第二套模型发现配置。
