# Uni-Lab 设备包 3D 模型存储规范

> 文档状态：建议规范  
> 整理日期：2026-07-29  
> 适用范围：Uni-Lab 外部设备包、设备驱动、资源定义、Edge 本地 3D 场景、RViz 和 MoveIt  
> 核心目标：安装、升级或回滚设备包时，设备代码与其运行时 3D 模型保持同版本、同来源、可自动发现

## 1. 规范目标

本规范回答以下问题：

1. 3D 模型应该放在设备包的什么位置；
2. 模型是否可以直接放在驱动目录；
3. XACRO、URDF、GLB、STL、纹理和配置文件分别如何组织；
4. 模型怎样进入 Python wheel；
5. wheel 安装后 Edge 怎样发现并读取模型；
6. `mesh_path` 应该表示什么；
7. Web、RViz 和 MoveIt 怎样读取同一设备包中的模型；
8. 如何避免绝对路径、模型重复、版本错配和任意文件暴露。

最终需要达到：

```text
安装设备包
    │
    ├── 安装设备驱动
    ├── 安装 Profile
    ├── 安装工作流
    ├── 安装 3D 模型
    └── 写入模型发现元数据
            │
            ▼
        Edge 启动发现
            │
            ├── Web 3D 可读取
            ├── RViz 可读取
            └── MoveIt 可读取
```

模型不再是 Uni-Lab-OS 主仓库中的一份独立副本，而是设备包版本的一部分。

## 2. 核心规范

### 2.1 推荐结论

模型可以直接放在对应驱动目录中，而且这是推荐方式。

这里的“直接放在驱动目录”是指：

```text
一台逻辑设备
└── 一个独立目录
    ├── driver.py
    ├── macro_device.xacro 或 model.glb
    ├── config/
    ├── meshes/
    └── textures/
```

不建议把所有文件完全平铺：

```text
robot.py
base.stl
link1.stl
link2.stl
joint.yaml
texture.png
...
```

推荐按设备建立目录，并在目录内部区分配置、视觉网格、碰撞网格和纹理。

### 2.2 必须保留包级模型清单

模型虽然与驱动放在一起，但设备包必须有一个统一的：

```text
model_manifest.yaml
```

Edge 读取清单发现模型。

Edge 不应递归扫描每个驱动文件夹，并根据文件名猜测哪个文件是模型入口。

因此推荐关系是：

```text
驱动目录
  → 保存模型实际文件

model_manifest.yaml
  → 保存模型索引、用途、identity 和入口相对路径
```

### 2.3 运行时模型必须进入 wheel

设备包的运行时模型必须位于 Python package 目录内，并通过 package data 写入
wheel。

只放在 Git 仓库中但没有进入 wheel，不算完成设备模型打包。

### 2.4 禁止保存宿主机绝对路径

设备包不得依赖：

```text
/home/user/project/...
/opt/unilab/...
C:\Users\...
file:///home/...
```

XACRO、manifest、Profile 和设备声明中只能保存：

- 稳定模型 key；
- bundle key；
- 包内相对路径；
- 由 Edge 运行时注入的资源根。

### 2.5 一个模型 Registry 负责全部读取

Edge 应通过统一模型 Registry 同时为不同消费者提供：

```text
HTTP URL       → Web 3D
本地文件路径   → XACRO、RViz、MoveIt
```

Web、RViz 和 MoveIt 不应各自扫描设备包。

### 3.3 整个工作站模型放在哪里

如果模型描述的是整个 SZLab 工作站，而不是某个独立工位，仍把它视为一个逻辑
device：

```text
devices/
└── szlab_poly_studio/
    ├── macro_device.xacro
    ├── model.glb
    ├── meshes/
    ├── config/
    └── textures/
```

不要在包根直接放：

```text
szlab_poly_studio/
├── station.glb
├── base.stl
└── robot.stl
```

因为缺少设备 identity 层级，后续难以判断这些模型属于整个工作站还是某个子设备。

### 3.4 共享模型放在哪里

仅被一个设备使用的文件必须放在该设备目录。

被两个或更多设备共同使用的文件可以放在：

```text
shared/
├── meshes/
├── materials/
└── textures/
```

例如：

```text
shared/meshes/common_emergency_button.glb
shared/textures/stainless_steel.png
```

不要通过文件系统符号链接共享模型资源。符号链接进入 wheel 后的行为不够稳定，
也会增加 Edge 路径越界校验的复杂度。

## 4. 驱动目录内部规范

### 4.1 推荐布局

一台设备的标准目录：

```text
devices/<device_key>/
├── __init__.py
├── driver.py
├── macro_device.xacro
├── model.glb
├── config/
│   ├── joint_limits.yaml
│   ├── initial_positions.yaml
│   ├── kinematics.yaml
│   └── materials.xacro
├── meshes/
│   ├── visual/
│   └── collision/
├── textures/
└── preview/
```

并非所有设备都必须包含所有文件。

### 4.2 静态设备最小结构

静态设备只需要浏览器展示时：

```text
devices/static_station/
├── __init__.py
├── driver.py
└── model.glb
```

如果需要简单碰撞几何：

```text
devices/static_station/
├── driver.py
├── model.glb
└── collision.stl
```

### 4.3 有关节设备最小结构

机械臂、滑轨、夹爪等有关节设备：

```text
devices/robot_arm/
├── __init__.py
├── driver.py
├── macro_device.xacro
├── config/
│   ├── joint_limits.yaml
│   └── initial_positions.yaml
└── meshes/
    ├── visual/
    │   ├── base.stl
    │   └── link_1.stl
    └── collision/
        ├── base.stl
        └── link_1.stl
```

### 4.4 原始 CAD 文件不属于运行时目录

以下文件通常不应进入设备 wheel：

```text
.step
.stp
.sldprt
.sldasm
.iges
.igs
Blender 工作文件
大型未优化 CAD 导出
```

这些是模型源文件，不是 Edge 运行时资源。

推荐在仓库中另设：

```text
model_sources/
└── ...
```

或使用受控的 CAD/大文件存储。

设备 wheel 中只保存经过优化、可直接加载的运行时产物：

```text
.xacro
.urdf
.srdf
.glb
.gltf
.stl
.dae
.obj
.yaml
纹理图片
```

如果原始 CAD 受许可限制，必须同时遵守模型来源的分发许可。

## 5. 文件和目录命名

### 5.1 设备 key

推荐使用：

```text
snake_case
```

例如：

```text
szlab_mixer_robot
szlab_s08_cap_station
```

不推荐：

```text
SZLab Mixer Robot
szlab-mixer-robot
robot final v2
```

### 5.2 四个 identity 应尽量一致

对于 XACRO 设备，以下名称应一致：

```text
@device id
目录名
model key
XACRO macro 名
```

例如：

```text
@device id       = szlab_mixer_robot
目录名           = devices/szlab_mixer_robot
model key        = szlab_mixer_robot
XACRO macro 名   = szlab_mixer_robot
```

这样可以减少映射配置和前端推导错误。

### 5.3 XACRO 入口文件名

统一使用：

```text
macro_device.xacro
```

因为现有 Uni-Lab 模型和前端已经使用这一约定。

### 5.4 GLB 入口文件名

如果设备只有一个 GLB：

```text
model.glb
```

整个工作站静态表示也可以使用更明确的名称：

```text
workcell.glb
```

但入口必须在 manifest 中显式声明，Edge 不通过文件名猜测。

### 5.5 网格文件名

推荐：

```text
base.stl
link_1.stl
link_2.stl
gripper_left.stl
gripper_right.stl
```

不推荐：

```text
零件1.STL
new final.STL
base_link_copy_2.STL
```

文件名必须：

- 跨平台；
- 不含空格；
- 不依赖大小写区分；
- 不包含本地设计人员姓名；
- 不使用“final”“new”等不可版本化含义。

## 6. 模型格式分工

### 6.1 XACRO

XACRO 用于表达：

- link；
- joint；
- visual；
- collision；
- 参数化结构；
- 重复机构；
- 不同设备型号；
- 初始关节值；
- 关节限制；
- 安装 link；
- ROS robot description。

适合：

- 机械臂；
- 滑轨；
- 夹爪；
- 有可动门或盖的工位；
- 需要 RViz 或 MoveIt 的设备。

### 6.2 URDF

URDF 可以是：

- 人工维护的简单运动学模型；
- XACRO 构建生成的固定产物；
- Web XACRO parser 的兼容产物。

如果 URDF 由 XACRO 生成，应在文件或构建脚本中明确：

```text
generated file; do not edit manually
```

不要同时手工维护内容不同的 XACRO 和 URDF。

### 6.3 GLB/GLTF

GLB/GLTF 用于：

- 静态设备；
- 工作站外壳；
- 物料；
- 带 PBR 材质的 Web 模型；
- 减少大量独立 STL 请求；
- 提高浏览器加载效率。

优先使用 GLB，因为它通常可以把几何、材质和纹理放在一个文件中。

### 6.4 STL

STL 适合：

- XACRO/URDF 的子网格；
- 简化 collision；
- 不需要材质的简单资源。

STL 不携带可靠的单位和材质信息，因此：

- 必须统一导出单位；
- 或在 XACRO 中明确 `scale`；
- 不建议将复杂静态整机拆成几十个 STL 供浏览器单独请求。

### 6.5 视觉与碰撞模型分离

视觉模型：

```text
meshes/visual/
```

可以有较高面数和完整外观。

碰撞模型：

```text
meshes/collision/
```

应该：

- 低面数；
- 封闭；
- 减少小零件；
- 减少自相交；
- 优先规划稳定性。

禁止默认把高精度视觉 CAD 网格直接作为 MoveIt collision 网格。

### 6.6 推荐格式表

| 对象 | Web 表示 | 运动学表示 | 碰撞表示 |
| --- | --- | --- | --- |
| 静态工作站外壳 | GLB | 无或简单 URDF | primitive/低面数 STL |
| 机械臂 | XACRO 或分 link mesh | XACRO/URDF | 低面数 STL |
| 滑轨 | XACRO | XACRO/URDF | 低面数 STL |
| 静态工位 | GLB | 通常无 | primitive/低面数 STL |
| 有开关盖机构的工位 | XACRO | XACRO/URDF | 低面数 STL |
| 烧杯、瓶、粉罐 | GLB | 无 | primitive/低面数 STL |
| 枪头 | 小 GLB/实例化 | 无 | 通常不逐个建 collision |

## 7. 坐标系、单位和模型原点

### 7.1 XACRO/URDF 坐标

设备 XACRO/URDF 推荐遵循 ROS 坐标约定：

```text
X：向前
Y：向左
Z：向上
```

旋转使用弧度。

### 7.2 长度单位

XACRO/URDF 中统一使用：

```text
meter
```

如果 CAD/STL 按毫米导出，应在导出阶段转换，或在 XACRO 中明确：

```xml
<mesh filename="..." scale="0.001 0.001 0.001" />
```

不能依赖 STL 文件自身表达单位，因为 STL 通常不携带单位语义。

### 7.3 GLB 单位和坐标轴

GLTF/GLB 通常以米为单位，并采用 Y-up 约定。

manifest 必须明确：

```yaml
coordinates:
  units: meter
  up_axis: y
```

XACRO/URDF 则通常是：

```yaml
coordinates:
  units: meter
  up_axis: z
```

### 7.4 设备原点

设备模型原点必须是稳定、可说明的安装原点，例如：

- 设备底座中心；
- 设备左前安装角；
- 机械臂 `base_link`；
- 工位定位销；
- 工作站世界坐标基准。

禁止使用：

- CAD 导出时随机保留的建模原点；
- 为某张截图临时移动后的原点；
- 随模型版本变化的包围盒中心。

### 7.5 模型姿态修正

如果模型源坐标不能修改，可以在 manifest 中声明固定变换：

```yaml
transform:
  position: [0.0, 0.0, 0.0]
  rotation_rpy: [0.0, 0.0, 0.0]
  scale: [1.0, 1.0, 1.0]
```

这类变换属于模型定义。

设备在实验室中的摆放位置则属于设备图或物料图，不应写入通用模型 manifest。

## 8. `model_manifest.yaml`

### 8.1 清单位置

推荐放在 Python package 根：

```text
szlab_poly_studio/model_manifest.yaml
```

它与：

```text
devices/
resources/
shared/
```

共享同一个包内相对路径根。

### 8.2 清单示例

```yaml
schema_version: 1

bundle:
  id: szlab-poly-studio
  display_name: SZLab 聚合物工作站模型包
  source_namespace: szlab

models:
  - key: szlab_poly_studio
    display_name: SZLab 聚合物工作站整机

    applies_to:
      - kind: resource
        class: szlab_poly_studio_deck

    representations:
      web:
        format: gltf
        entry: devices/szlab_poly_studio/workcell.glb

      kinematics:
        format: xacro
        entry: devices/szlab_poly_studio/macro_device.xacro
        macro: szlab_poly_studio

      collision:
        format: xacro
        entry: devices/szlab_poly_studio/macro_device.xacro
        macro: szlab_poly_studio

    coordinates:
      units: meter
      up_axis: z

    transform:
      position: [0.0, 0.0, 0.0]
      rotation_rpy: [0.0, 0.0, 0.0]
      scale: [1.0, 1.0, 1.0]

  - key: szlab_mixer_robot
    display_name: SZLab 搬运机械臂

    applies_to:
      - kind: device
        class: szlab_mixer_robot

    representations:
      web:
        format: xacro
        entry: devices/szlab_mixer_robot/macro_device.xacro
        macro: szlab_mixer_robot

      kinematics:
        format: xacro
        entry: devices/szlab_mixer_robot/macro_device.xacro
        macro: szlab_mixer_robot

      collision:
```

### 8.3 representation

同一个模型 key 可以有不同用途的表示：

```text
web
kinematics
collision
```

Edge 根据消费者选择表示：

```text
Web/Pascal/Three.js  → web
RViz                 → kinematics
MoveIt               → kinematics + collision
```

如果第一版只有一个 XACRO，可以：

```yaml
representations:
  web:
    format: xacro
    entry: devices/szlab_mixer_robot/macro_device.xacro
    macro: szlab_mixer_robot
  kinematics:
    format: xacro
    entry: devices/szlab_mixer_robot/macro_device.xacro
    macro: szlab_mixer_robot
```

### 8.4 清单路径规则

所有 `entry`：

- 必须是 package 根下的相对路径；
- 必须使用 `/`；
- 不允许绝对路径；
- 不允许 `..` 越界；
- 不允许临时 URL；
- 不允许指向设备包之外；
- 必须在构建和 Edge 启动时校验存在。

### 8.5 模型匹配

推荐匹配优先级：

1. 图节点显式 `bundle + model key`；
2. `@device` / `@resource` 显式模型引用；
3. manifest 中 `applies_to.class` 精确匹配；
4. 旧模型 token 匹配；
5. 无模型。

新设备包不得把模糊字符串匹配作为主要模型绑定方式。

## 9. 设备与资源声明

### 9.1 `@device`

设备类只引用稳定模型 identity：

```python
@device(
    id="szlab_mixer_robot",
    display_name="SZLab 搬运机械臂",
    category=["custom", "robotic_arm"],
    model={
        "bundle": "szlab-poly-studio",
        "key": "szlab_mixer_robot",
    },
)
class SZLabMixerRobot:
    ...
```

不要写：

```python
model={
    "path": "/home/user/Uni-Lab-SZLab/robot.xacro",
}
```

### 9.2 `@resource`

资源同样引用模型 identity：

```python
@resource(
    id="szlab_beaker_500ml",
    displayname="SZLab 500 mL 烧杯",
    category=["szlab_poly_studio", "container", "beaker"],
    model={
        "bundle": "szlab-poly-studio",
        "key": "szlab_beaker_500ml",
    },
)
def beaker_500ml(...):
    ...
```

### 9.3 图节点覆盖

只有实例确实需要不同模型时，才在图节点覆盖：

```json
{
  "id": "szlab_mixer_robot_2",
  "type": "device",
  "class": "szlab_mixer_robot",
  "model": {
    "bundle": "szlab-poly-studio",
    "key": "szlab_mixer_robot_long_rail"
  }
}
```

默认模型不应在每个图实例中重复。

## 10. XACRO 与 `mesh_path`

### 10.1 `mesh_path` 的标准含义

本规范继续保留参数名：

```text
mesh_path
```

但它的实际含义定义为：

> 当前设备包的运行时模型资源根，而不仅是某个 `meshes/` 子目录。

资源根下可以包含：

```text
devices/
resources/
shared/
```

### 10.2 标准 XACRO

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://ros.org/wiki/xacro">
  <xacro:macro
    name="szlab_mixer_robot"
    params="
      mesh_path:=''
      parent_link:=''
      station_name:=''
      device_name:=''
    ">

    <xacro:property
      name="joint_limits"
      value="${xacro.load_yaml(
        mesh_path +
        '/devices/szlab_mixer_robot/config/joint_limits.yaml'
      )}" />

    <link name="${device_name}base_link">
      <visual>
        <geometry>
          <mesh
            filename="file://${mesh_path}/devices/szlab_mixer_robot/meshes/visual/base.stl" />
        </geometry>
      </visual>

      <collision>
        <geometry>
          <mesh
            filename="file://${mesh_path}/devices/szlab_mixer_robot/meshes/collision/base.stl" />
        </geometry>
      </collision>
    </link>
  </xacro:macro>
</robot>
```

### 10.3 Web 的 `mesh_path`

Edge 对外提供：

```text
/api/v1/model-bundles/
  szlab-poly-studio/
  {revision}/
  assets/
  devices/
  szlab_mixer_robot/
  macro_device.xacro
```

前端传入：

```text
mesh_path =
/api/v1/model-bundles/szlab-poly-studio/{revision}/assets
```

XACRO 中的 mesh 会请求：

```text
/api/v1/model-bundles/
  szlab-poly-studio/
  {revision}/
  assets/
  devices/
  szlab_mixer_robot/
  meshes/
  visual/
  base.stl
```

### 10.4 ROS 的 `mesh_path`

wheel 安装后，Edge 本地模型根可能为：

```text
/.../site-packages/szlab_poly_studio
```

ROS 调用 XACRO 时传入：

```text
mesh_path=/.../site-packages/szlab_poly_studio
```

同一份 XACRO 会解析到：

```text
/.../site-packages/
  szlab_poly_studio/
  devices/
  szlab_mixer_robot/
  meshes/
  visual/
  base.stl
```

这使一份 XACRO 同时适用于：

- Edge HTTP；
- 本地 XACRO；
- RViz；
- MoveIt。

### 10.5 为什么 `macro_device.xacro` 与驱动同级

当前前端会从入口 XACRO 的父目录推导宏名。

入口：

```text
devices/szlab_mixer_robot/macro_device.xacro
```

推导宏名：

```text
szlab_mixer_robot
```

因此推荐：

```text
devices/szlab_mixer_robot/
├── driver.py
└── macro_device.xacro
```

不推荐：

```text
devices/szlab_mixer_robot/
├── driver.py
└── model/
    └── macro_device.xacro
```

后者会让当前前端错误推导宏名为 `model`。

如果未来前端改为从 manifest 显式读取 `macro`，才可以解除这一目录约束。

### 10.6 禁止 `$(find package)`

设备包 XACRO 不应依赖：

```xml
$(find some_ros_description_package)
```

因为外部设备 Python wheel 不一定同时是 ROS ament package，浏览器 XACRO parser
也不能可靠解析 ROS package index。

统一使用：

```text
mesh_path + 包内相对路径
```

```toml
[project.entry-points."unilabos.model_bundles"]
```

```python
def get_model_bundle() -> dict[str, str]:
    return {
        "package": "szlab_poly_studio",

```

- 连接 OPC UA；
- 创建串口；
- 创建设备实例；
- 启动线程；
- 启动 ROS；
- 加载真实硬件凭证。

### 11.3 wheel 内容检查

构建后必须检查 wheel，而不仅检查源码：

```bash
unzip -l dist/szlab/unilabos_szlab_poly_studio-*.whl
```

应该出现：

```text
szlab_poly_studio/model_manifest.yaml
szlab_poly_studio/devices/.../macro_device.xacro
szlab_poly_studio/devices/.../model.glb
szlab_poly_studio/devices/.../meshes/...
szlab_poly_studio/resources/.../model.glb
```

不应出现：

```text
日志
SQLite
缓存
用户名密码
本地测试输出
原始未优化 CAD
```

### 11.4 超大模型包

默认情况下，模型应直接包含在设备 wheel 中。

如果模型资源过大，确实不适合与驱动代码放在同一个 wheel，可以拆成配套
distribution：

```text
unilabos-szlab-poly-studio
  depends on
unilabos-szlab-poly-studio-models == 相同兼容版本
```

此时仍必须保证：

- 安装设备包会自动安装模型包；
- 版本约束明确；
- 回滚设备包同时回滚模型；
- Edge 使用同样的 bundle discovery；
- 不能要求用户手动去另一个目录复制模型。

## 12. Edge 发现和读取

### 12.1 启动流程

```text
Edge 启动
  │
  ├── 读取内置模型 bundle
  │
  ├── 读取 importlib.metadata.entry_points()
  │
  ├── 选择 unilabos.model_bundles
  │
  ├── 定位 model_manifest.yaml
  │
  ├── 校验 manifest
  │
  ├── 校验模型入口
  │
  ├── 校验路径未越界
  │
  ├── 计算 bundle revision
  │
  └── 建立 identity → model 索引
```

### 12.2 模型 Registry 接口

Edge 推荐通过统一模块提供：

```python
list_bundles()
model_for_node(node, consumer="web")
resolve_public_url(model_ref)
resolve_local_asset(model_ref)
resolve_bundle_asset(bundle_id, revision, relative_path)
```

Material API、RViz 和 MoveIt 只能通过该 Registry 读取模型。

### 12.3 Web URL

推荐：

```text
GET /api/v1/model-bundles
GET /api/v1/model-bundles/{bundle_id}
GET /api/v1/model-bundles/{bundle_id}/{revision}/assets/{asset_path}
```

示例：

```text
GET /api/v1/model-bundles/
    szlab-poly-studio/
    abc123/
    assets/
    devices/
    szlab_mixer_robot/
    macro_device.xacro
```

URL 中必须包含：

- bundle ID；
- content revision；
- 包内相对路径。

URL 中不得包含：

- `site-packages` 绝对路径；
- 用户目录；
- Python module 文件路径；
- 本地磁盘盘符。

### 12.4 Material API 返回示例

```json
{
  "rendering": {
    "kind": "robotic-arm",
    "dimensionsMm": [1200, 1800, 1200],
    "scale": [1, 1, 1],
    "model": {
      "bundle": "szlab-poly-studio",
      "key": "szlab_mixer_robot",
      "path": "/api/v1/model-bundles/szlab-poly-studio/abc123/assets/devices/szlab_mixer_robot/macro_device.xacro",
      "format": "xacro",
      "position": [0, 0, 0],
      "rotation": [0, 0, 0],
      "attachPoints": []
    }
  }
}
```

### 12.5 安装后的自动性

正确行为：

```text
pip install 设备 wheel
→ 模型文件进入 site-packages
→ entry point 进入 distribution metadata
→ 重启 Edge
→ Edge 自动发现模型
```

不要求：

- 手动复制到 `unilabos/device_mesh`；
- 修改 Uni-Lab-OS 源码；
- 配置宿主机绝对路径；
- 把模型上传到临时 OSS；
- 在前端内置模型文件。

第一版可以要求安装或卸载设备包后重启 Edge，不建议立即实现运行中热加载。

## 13. 资源接口安全

### 13.1 不能公开整个 Python package

模型与驱动同目录后，模型资源根同时包含：

```text
driver.py
__init__.py
```

因此 Edge 不能简单执行：

```text
StaticFiles(directory=整个设备包目录)
```

否则可能把 Python 源码、配置甚至敏感文件作为静态资源公开。

### 13.2 允许的文件

建议允许：

```text
.xacro
.urdf
.srdf
.yaml
.yml
.stl
.dae
.obj
.mtl
.gltf
.glb
.png
.jpg
.jpeg
.webp
```

### 13.3 禁止的文件

至少禁止：

```text
.py
.pyc
.so
.dll
.exe
.env
.db
.sqlite
.sqlite3
.log
.pkl
```

### 13.4 路径限制

Edge 必须：

1. 从已登记 bundle 找到资源根；
2. 将 URL 路径作为相对路径处理；
3. 执行规范化和 `resolve()`；
4. 确认解析结果仍在 bundle 根内；
5. 检查扩展名；
6. 检查文件属于允许的模型资源；
7. 再返回文件。

必须拒绝：

```text
../../driver.py
../../.env
/etc/passwd
C:\Users\...
```

### 13.5 是否只允许 manifest 显式列出的文件

模型入口必须在 manifest 中显式列出。

XACRO 的依赖文件可以采用两种策略：

1. 启动时解析 XACRO/URDF 依赖闭包，只有依赖闭包内文件可以访问；
2. 允许访问设备目录下的模型扩展名，但禁止代码和越界。

第一种更严格，第二种实现更简单。

无论采用哪种，都不能把整个 Python package 无限制公开。

## 14. 版本和缓存

### 14.1 模型版本跟随 distribution

推荐：

```text
unilabos-szlab-poly-studio 0.2.0
├── 驱动
├── Profile
├── 工作流
└── 模型
```

模型不需要再维护一个与设备 wheel 无关的人工版本。

### 14.2 模型 key 保持稳定

例如：

```text
szlab_mixer_robot
```

模型文件可以更新，但稳定 model key 不应因为文件改名而改变。

### 14.3 revision

Edge 根据以下信息生成 revision：

- distribution 版本；
- manifest 内容；
- 模型入口和依赖文件 hash。

公开 URL：

```text
/api/v1/model-bundles/{bundle}/{revision}/assets/...
```

模型内容改变时 revision 必须改变。

### 14.4 HTTP 缓存

包含 revision 的模型文件可以返回：

```text
Cache-Control: public, max-age=31536000, immutable
ETag: "<asset-hash>"
```

这样升级模型后使用新 URL，旧模型不会污染新版本。

## 15. 整机模型与独立设备模型

### 15.1 整机组合模型

可以将整个 SZLab 保存为：

```text
devices/szlab_poly_studio/
├── workcell.glb
└── macro_device.xacro
```

适合：

- 第一阶段快速展示完整工作站；
- 当前设备图没有准确子设备 pose；
- 固定设施很多；
- 暂时不需要每个工位独立选中。

### 15.2 独立设备模型

每个工位独立保存：

```text
devices/szlab_mixer_stirrer/model.glb
devices/szlab_mixer_pump/model.glb
devices/szlab_s08_cap_station/macro_device.xacro
```

适合：

- 每个设备节点需要独立选中；
- 每个设备有状态动画；
- 设备可以独立复用；
- 图中的 parent 和 pose 已经准确。

### 15.3 防止重复渲染

如果整机模型已经包含机械臂，而机械臂节点又绑定独立模型，会出现：

```text
两个重叠机械臂
```

必须明确每段物理几何由谁负责渲染。

推荐两阶段：

```text
阶段 1
  整机静态 GLB
  + 独立机械臂 XACRO
  + 独立物料 GLB

阶段 2
  校准所有设备 pose
  → 拆分各工位模型
  → 从整机底模中删除已独立渲染的几何
```

- 关键 link 与机械臂点位坐标系一致。

## 17. 禁止事项

设备包模型禁止：

- 只存在源码仓库、不进入 wheel；
- 复制到 Uni-Lab-OS 的 `device_mesh` 才能工作；
- 写死开发机路径；
- 写死用户目录；
- 写死临时 OSS URL；
- 通过 `$(find ...)` 依赖未声明的 ROS description package；
- 让 Edge 扫描整个 `site-packages` 猜测模型；
- 让 HTTP 静态服务公开整个 Python package；
- 使用安装顺序解决模型 identity 冲突；
- 把高精度 visual mesh 直接作为默认 collision；
- 手工维护互相不一致的 XACRO 和生成 URDF；
- 把整机模型和独立子设备模型重复渲染；
- 在模型中固化某个实验室实例的世界坐标；
- 把日志、数据库、缓存或凭证打入模型包；
- 依赖符号链接越出设备包。

## 19. 最终标准模板

### 19.1 目录

```text
distribution/
├── pyproject.toml
└── python_package/
    ├── model_bundle.py
    ├── model_manifest.yaml
    ├── devices/
    │   └── <device_key>/
    │       ├── driver.py
    │       ├── macro_device.xacro
    │       ├── model.glb
    │       ├── config/
    │       ├── meshes/
    │       │   ├── visual/
    │       │   └── collision/
    │       └── textures/
    ├── resources/
    │   └── <resource_key>/
    │       ├── definition.py
    │       ├── model.glb
    │       └── collision.stl
    └── shared/
```

### 19.2 模型引用

```python
model={
    "bundle": "vendor-device-package",
    "key": "device_key",
}
```

### 19.3 XACRO 路径

```xml
filename="file://${mesh_path}/devices/device_key/meshes/visual/base.stl"
```

### 19.4 Web 资源根

```text
mesh_path =
/api/v1/model-bundles/{bundle}/{revision}/assets
```

### 19.5 本地资源根

```text
mesh_path =
/.../site-packages/{python_package}
```

### 19.6 安装行为

```text
安装 wheel
→ 安装驱动和模型
→ Edge 通过 entry point 发现 manifest
→ Web 和 ROS 通过统一模型 Registry 读取
```
